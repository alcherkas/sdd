Root Causes

Context Window LimitsAI loses track of requirements across sessions. Later sections get less attention.
Non-DeterminismSame prompt, different outputs. No structural anchor means no reproducibility.
Instruction-Data ConfusionAI cannot distinguish intent from content. Specs in context window compete with code.
Architectural DriftEach generation session drifts independently. No cross-session coherence.

The Vibe Coding Problem

Vibe Coding (Andrej Karpathy, Feb 2025): “You fully give in to the vibes, embrace exponentials, and forget that the code even exists.” This works for prototypes but fails catastrophically for production systems where reliability, security, and maintainability matter.
The SDD thesis: SDD inverts the relationship — the spec is maintained, code is generated. Instead of trying to control AI output through better prompts, we control it through better specifications. The spec becomes the source of truth; code is a disposable artifact.
“With the compressed code cycles, there should be plenty of time to communicate. If it’s not happening, it’s because nobody wants to communicate.” — Vaughn Vernon

PHASE 1

Define: Requirements

Before any AI prompt, write down what you want and why. Every requirement must be testable.

Goal StatementOne sentence: what does the feature do and why does it exist? This anchors all downstream generation.
Functional RequirementsNumbered list of behaviors. Each must be independently testable. Use “shall” language.
Success CriteriaHow do you know it works? Quantitative where possible: latency < 200ms, error rate < 0.1%.
Out of ScopeExplicitly state what the feature does NOT do. Prevents AI from gold-plating or drifting into adjacent features.

Feature Spec Template


# Feature: [Name]

## Goal
[One sentence: what and why]

## Functional Requirements
1. The system shall [behavior 1]
2. The system shall [behavior 2]
3. The system shall [behavior 3]

## Non-Functional Requirements
- Latency: p99 < [target]ms
- Error rate: < [target]%
- Compatibility: [browsers/platforms]

## Success Criteria
- [ ] All functional requirements pass automated tests
- [ ] Performance meets NFR targets
- [ ] No new lint/type errors introduced

## Out of Scope
- [Feature X] (deferred to next sprint)
- [Integration Y] (separate spec)

## Open Questions
- [?] [Unresolved decision — block generation until answered]
PHASE 2

Decompose: Design

Break the feature into components with explicit interfaces. AI generates best when scope is narrow and contracts are clear.

Interface ContractsDefine inputs, outputs, and error cases for each component boundary. TypeScript types, API schemas, or function signatures.
Data ModelsEntity relationships, state machines, and data flow. Generation sessions need a shared structural anchor.
Task BreakdownEach generation task should be scoped to a single component or concern. One task = one context window.

Why Decomposition Matters

ApproachBest ForOutput
Monolithic promptTiny scripts, one-off tasksSingle file, no structure guarantees
Component-level tasksFeatures with 2-5 modulesEach module fits in context, interfaces enforced
Micro-task decompositionComplex systems, teamsEach task < 2K tokens of spec, highly reproducible
Rule of thumb: If your spec exceeds 2,000 tokens, decompose further. AI attention degrades significantly beyond this threshold.
Monolithic generation is the #1 cause of architectural drift. Each session independently invents structure instead of following a shared design.
PHASE 3

Constrain: Guardrails

Define what AI can and cannot do. Without explicit constraints, agents take the path of least resistance.

Three-Tier Permission Model

TierPolicyExamples
AlwaysAI can do without askingRun tests, format code, read files
Ask FirstRequires human approvalInstall packages, modify configs, delete files
NeverHard stop, deniedPush to main, run sudo, access .env
Without “Never” rules, AI agents will eventually execute destructive operations. Default-allow is the root cause of most agent incidents.

PHASE 4

Generate: Context Engineering

Generation quality is a function of context quality. Layer your context from global to task-specific.

Global Context (CLAUDE.md)Project-wide standards, patterns, and constraints. Loaded automatically every session.
Project Context (Spec Files)Feature specs, interface contracts, data models. Referenced explicitly per task.
Session Context (Conversation)Current discussion thread. Degrades as conversation grows. Keep sessions focused.
Task Context (Current Prompt)The specific instruction for this generation. Include only what’s needed for this one task.

PHASE 5

Verify: Validation

Every generation must be verified against the spec before merging. Trust but verify — or better, don’t trust at all.

Automated TestsUnit, integration, and E2E tests written from spec before code generation. Tests are the executable spec.
Spec-Compliance CheckSystematically verify each requirement. Checklist-driven: every “shall” in the spec gets a pass/fail.
LLM-as-JudgeUse a separate AI session to review generated code against the spec. Different context = different blind spots.
Human ReviewFinal gate. Focus on architectural decisions, security implications, and spec ambiguities the AI may have resolved incorrectly.

The Harness Feedback Loop

Spec-to-implementation gap → strengthen validation. When generated code doesn’t match the spec, add more specific constraints and test criteria to prevent recurrence.
Intent-to-specification gap → improve elicitation. When the spec itself was wrong, refine the Define phase templates and checklists to catch ambiguity earlier.
Each gap strengthens the harness for ALL future work. Unlike code fixes that are local, harness improvements are global. A better spec template improves every feature. A better constraint set prevents entire categories of errors.

SDD Anti-Patterns

Critical The Spec Novel Specs exceeding 5,000 words. AI loses early requirements as later sections dominate attention. Fix: layer specs, each under 2K tokens.
Critical Skipping Verification Trusting AI output without checking against spec. Drift accumulates silently. Fix: mandatory verification before merge.
High Spec-and-Forget Spec written once, never updated. Subsequent AI sessions use outdated context. Fix: treat specs as living documents, update during verification.
High One Giant Prompt Entire project spec in a single session. Internally inconsistent output. Fix: decompose into focused tasks with scoped specs.

↓ more anti-patterns

More Anti-Patterns

High Vibe Spec Vague language: “make it fast,” “follow best practices.” No measurable definitions. Fix: every requirement must be testable.
Medium Implementation Spec Dictating exact code structure instead of behavior. Fix: specify what and why, not how.
Medium Copy-Paste Architecture AI replicates training data patterns instead of matching your architecture. Fix: explicit Constraint Specs with code examples.
High Spec Without Tests Requirements with no verification criteria. Acceptance = “it looks right.” Fix: include test criteria in every spec.

Precision & the Spec-as-Code Debate

“Vibe coding gives the illusion that your vibes are precise abstractions. They will feel this way right up until they leak, which will happen when you add enough features or get enough scale.” — Steve Krouse
Vibe Code = Legacy Code Karpathy’s “forget the code even exists” produces code nobody understands — we already have a name for that: legacy code. It resists modification and hides bugs.
Programming = Theory Building Peter Naur’s insight: the value of a developer is the mental model, not the text produced. Specs encode that theory; vibe coding skips it entirely.
The precision thesis: Even with AGI, the first use will be building better abstractions to master complexity. AI raises the ceiling on abstraction — it doesn’t remove the need for it. Specs are the abstraction layer between intent and generated code.

↓ the spec-as-code counterargument

A Sufficiently Detailed Spec Is Code

“If you try to make a specification document precise enough to reliably generate a working implementation, you must necessarily contort the document into code or something strongly resembling code.” — Gabriella Gonzalez
Spec PrecisionWhat HappensImplication
Low Vague languageAI generates plausible but incorrect codeHigh error rate, unreliable output
Medium Structured reqsBetter output but gaps at edge casesSweet spot for SDD — reviewable + useful
High Fully preciseSpec becomes indistinguishable from codeNo simplification achieved
The shared insight: Complexity is conserved. SDD doesn’t eliminate complexity — it relocates it from opaque generated code into reviewable, version-controlled specifications. Don’t promise “no more coding” — promise explicit, reviewable intent.

Enterprise SDD Adoption

Core insight: SDD at enterprise scale cannot be treated as a technical rollout. It shifts delivery from tactical prompting to collaborative intent articulation — requiring workflow, tooling, and organizational change.
Tooling Gaps Most SDD tools optimize for single-developer workflows. Enterprise scale requires multi-repo coordination and cross-project dependency tracking.
Workflow Integration Teams use Jira, Azure DevOps, or Linear. SDD must integrate with existing backlogs as a communication bridge, not replace them.
Brownfield Reality Existing codebases lack specifications. Progressive spec growth (not reverse-engineering) is the only viable path at scale.
Cross-Functional Access Product, design, QA, and security all need spec access. Not everyone should need Git to participate in specification work.

Quick Start

  1. Write requirements before prompting
  2. Define interfaces before internals
  3. Set up project instructions (CLAUDE.md / .cursorrules)
  4. Include “never do” rules
  5. Use Plan Mode for exploration
  6. Decompose features into focused tasks
  7. Include test criteria in every spec
  8. Generate tests before implementation
  9. Verify every generation against spec
  10. Update specs when reality diverges
